# Skill: assistant-scenario-curator

## Purpose

Hans 하네스의 검증 시나리오를 작성한다. 시나리오는 실제 사용자가 입력할 법한 한국어 요청을 Markdown으로 기록하고, Pass/Fail 기준을 명확히 한다.

## Responsibilities

- `scenarios.md`에 기능별 샘플 입력을 작성한다.
- 정상, 경계, 실패 케이스를 분리한다.
- 각 시나리오의 검증 기준을 측정 가능한 문장으로 만든다.
- 개인정보나 실제 계정 정보를 포함하지 않는다.

## Scenario Structure

각 시나리오는 다음 구조를 따른다.

```text
## H-XXX. Feature Name

### 목적
기능이 검증하려는 사용자 문제.

### 샘플 입력
Markdown 표 또는 짧은 문단.

### 기대 결과
모델 또는 SDK가 반환해야 하는 결과.

### 검증 기준
Pass 조건과 Fail 조건이 나뉜 표.

### 경계 케이스
모호함, 빈 입력, 충돌 정보, 안전 제한.
```

## Writing Rules

- 샘플 입력은 현실적인 한국어로 작성한다.
- 한 시나리오는 하나의 핵심 기능을 검증한다.
- 날짜가 있으면 기준 시각과 timezone을 함께 둔다.
- OCR 또는 이미지 설명이 있으면 근거와 한계를 함께 검증한다.
- 기대 결과는 "좋은 답변"처럼 주관적으로 쓰지 않는다.

## Good Assertion Examples

| Weak | Better |
|------|--------|
| 좋은 요약을 만든다 | summary가 원문보다 짧고 keyPoints에 담당자와 업무가 포함된다 |
| 날짜를 잘 해석한다 | `내일 오후 3시`를 기준 시각과 timezone으로 정규화한다 |
| 액션을 잘 찾는다 | 담당자가 없는 항목은 assignee를 임의 생성하지 않는다 |
| 이미지를 이해한다 | OCR 근거를 evidence에 남기고 이미지 원본 부재를 warning으로 표시한다 |

## Privacy Rules

- 실제 전화번호, 이메일, 주소, 계좌번호를 넣지 않는다.
- 실사용자 이름이 필요하면 흔한 가명만 사용한다.
- 민감한 건강, 금융, 신분 정보는 검증 목적이 명확할 때만 추상화해 쓴다.

## Review Checklist

- [ ] 시나리오 ID가 안정적이다.
- [ ] 샘플 입력이 실제 사용 상황에 가깝다.
- [ ] Pass/Fail 기준이 구분된다.
- [ ] 계약에 없는 결과 필드를 요구하지 않는다.
- [ ] JSON fixture 파일을 만들지 않았다.
